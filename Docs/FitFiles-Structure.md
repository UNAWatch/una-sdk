# FIT Files Structure in UNA SDK

This document provides a detailed analysis of the FIT (Flexible and Interoperable data Transfer) file structure generated by the `ActivityWriter` class in the UNA SDK. FIT is a binary file format used primarily for fitness data, such as activities recorded by devices like Garmin watches or fitness trackers. It is designed to be compact, extensible, and compatible across different platforms.

The UNA SDK uses the FIT protocol to serialize activity data (e.g., running, cycling, hiking, heart rate monitoring) into `.fit` files. This document covers the structure from basic concepts to advanced implementation details, focusing on the code usage in `ActivityWriter.cpp` across different apps (Running, Cycling, Hiking, HRMonitor).

## Introduction to FIT

### What is FIT?
FIT is a binary protocol developed by Garmin for storing fitness data. It supports various message types (e.g., records, sessions, laps) and allows for custom developer fields. Files are self-describing, meaning they include definitions for the data they contain.

### Key Concepts for Beginners
- **Messages**: Units of data in a FIT file, like "Record" for GPS points or "Session" for activity summaries.
- **Definitions**: Metadata describing the structure of messages (e.g., which fields are included).
- **Fields**: Individual data points within messages (e.g., timestamp, heart rate).
- **Developer Fields**: Custom fields added by developers, not part of the standard FIT profile.
- **CRC**: Cyclic Redundancy Check for data integrity.

### FIT Protocol Versions
The UNA SDK uses:
- Protocol Version: 2.0 (`FIT_PROTOCOL_VERSION_20`)
- Profile Version: As defined in `FIT_PROFILE_VERSION` (typically the latest supported)

## Overall FIT File Structure

A FIT file generated by `ActivityWriter` follows this sequence:

1. **File Header** (14 bytes): Contains size, protocol version, profile version, data size, and CRC.
2. **Data Section**: A series of messages (definitions followed by data).
3. **CRC** (2 bytes): Integrity check for the entire file.

The data section is written in the order defined in `ActivityWriter::start()`, `addRecord()`, `addLap()`, `stop()`, etc.

### Sequence of Messages
- File ID Message
- Developer Data ID Message
- Field Description Messages (for developer fields)
- Definition Messages (for Record, Lap, Session, Event, Activity)
- Data Messages:
  - Event (START)
  - Record Messages (multiple, as data is added)
  - Lap Messages (multiple, as laps are added)
  - Event (STOP)
  - Session Message
  - Activity Message

## Message Types and Fields

### File ID Message
- **Purpose**: Identifies the file type and creator.
- **Fields**:
  - `product_name`: "UNA Watch"
  - `serial_number`: 0
  - `time_created`: Unix timestamp converted to FIT time
  - `manufacturer`: `FIT_MANUFACTURER_DEVELOPMENT`
  - `product`: 0
  - `number`: 0
  - `type`: `FIT_FILE_ACTIVITY`

### Developer Data ID Message
- **Purpose**: Registers the developer and app for custom fields.
- **Fields**:
  - `developer_id`: App-specific developer ID
  - `application_id`: App-specific application ID
  - `application_version`: App version
  - `manufacturer_id`: `FIT_MANUFACTURER_DEVELOPMENT`
  - `developer_data_index`: 0

### Field Description Messages
- **Purpose**: Describe custom developer fields.
- **Fields** (per field):
  - `field_name`: e.g., "batteryLevel", "steps"
  - `units`: e.g., "%", "mV"
  - `developer_data_index`: 0
  - `field_definition_number`: Unique ID for the field
  - `fit_base_type_id`: Data type (e.g., `FIT_BASE_TYPE_UINT8`)

### Record Messages
- **Purpose**: Individual data points during the activity (e.g., every second).
- **Base Fields** (always present):
  - `timestamp`: FIT timestamp
  - `enhanced_altitude`: Altitude in mm (scaled)
  - `enhanced_speed`: Speed in mm/s (scaled)
  - `heart_rate`: BPM
- **Variants**:
  - Basic Record: No GPS or battery
  - Record with GPS: Adds `position_lat`, `position_long` (semicircles)
  - Record with Battery: Adds developer fields for battery level and voltage
  - Combined: GPS + Battery

### Lap Messages
- **Purpose**: Summarize data for each lap.
- **Fields**:
  - `message_index`: 0
  - `timestamp`: End time
  - `start_time`: Start time
  - `total_elapsed_time`: Time including pauses (ms)
  - `total_timer_time`: Active time (ms)
  - `total_distance`: Distance (cm)
  - `avg_speed`: Average speed (mm/s)
  - `max_speed`: Max speed (mm/s)
  - `avg_heart_rate`: Average HR
  - `max_heart_rate`: Max HR
  - `total_ascent`: Ascent (m)
  - `total_descent`: Descent (m)
- **Developer Fields**: Steps and floors (Hiking only)

### Session Messages
- **Purpose**: Overall activity summary.
- **Fields**: Similar to Lap, but for the entire session.
- **Additional**: `sport`, `sub_sport`, `num_laps`
- **Developer Fields**: Steps and floors (Hiking only)

### Event Messages
- **Purpose**: Mark start/stop/pause/resume events.
- **Fields**:
  - `timestamp`: Event time
  - `event`: `FIT_EVENT_TIMER`
  - `event_type`: START or STOP

### Activity Messages
- **Purpose**: Top-level activity info.
- **Fields**:
  - `timestamp`: Activity end time
  - `local_timestamp`: Local time
  - `total_timer_time`: Total active time (ms)
  - `num_sessions`: 1

## Activity-Specific Variations

### Running and Cycling
- **Sport**: `FIT_SPORT_RUNNING` or `FIT_SPORT_CYCLING`
- **Records**: Include GPS, speed, altitude, HR, battery
- **Laps/Sessions**: Full set of fields (distance, speed, elevation, HR)
- **Developer Fields**: Battery level (%), voltage (mV)

### Hiking
- **Sport**: `FIT_SPORT_HIKING`
- **Records**: Same as Running/Cycling
- **Laps/Sessions**: Adds steps (uint32) and floors (uint32) as developer fields
- **Developer Fields**: Steps, floors, battery level, voltage

### HRMonitor
- **Sport**: `FIT_SPORT_GENERIC`
- **Records**: Only timestamp, HR, trust level (uint8 %)
- **Laps/Sessions**: Minimal fields (no distance, speed, elevation)
- **No GPS or Battery Fields**

## Developer Fields

Developer fields extend standard FIT messages with custom data. They require:
1. A Developer Data ID message.
2. Field Description messages.
3. Usage in data messages via `writeFieldMessage()`.

### Battery Fields (Running, Cycling, Hiking)
- Field 2: `batteryLevel` (uint8, %)
- Field 3: `battVoltage` (uint16, mV)
- Attached to Record messages with battery data.

### Steps and Floors (Hiking)
- Field 0: `steps` (uint32)
- Field 1: `floors` (uint32)
- Attached to Lap and Session messages.

### Trust Level (HRMonitor)
- Field 0: `hr_trust_level` (uint8, percents)
- Attached to Record messages.

## Visual Representations

### FIT File Sequence Diagram
```
File Header
├── File ID
├── Developer Data ID
├── Field Descriptions (if any)
├── Definitions (Record, Lap, Session, Event, Activity)
├── Event (START)
├── Record 1
├── Record 2
├── ...
├── Lap 1
├── Lap 2
├── ...
├── Event (STOP)
├── Session
└── Activity
CRC
```

### Record Message Variants
```
Basic Record
├── timestamp
├── enhanced_altitude
├── enhanced_speed
└── heart_rate

Record + GPS
├── (Basic fields)
├── position_lat
└── position_long

Record + Battery
├── (Basic fields)
├── batteryLevel (dev field)
└── battVoltage (dev field)

Record + GPS + Battery
├── (Basic + GPS fields)
├── batteryLevel (dev field)
└── battVoltage (dev field)
```

### Message Flow in Code
```
start() -> Write header, File ID, Developer ID, Field Descs, Definitions, Event START
addRecord() -> Write Record message (variant based on data)
addLap() -> Write Lap message + dev fields
stop() -> Event STOP, Session + dev fields, Activity, update header, CRC
```

## Code Usage Examples

### Initializing Message Handlers
```cpp
mFHRecord.init({ FIT_RECORD_FIELD_NUM_TIMESTAMP,
                  FIT_RECORD_FIELD_NUM_ENHANCED_ALTITUDE,
                  FIT_RECORD_FIELD_NUM_ENHANCED_SPEED,
                  FIT_RECORD_FIELD_NUM_HEART_RATE });
```

### Writing a Record
```cpp
FIT_RECORD_MESG msg = prepareRecordMsg(record);
if (record.hasBattery()) {
    mFHRecordGB.writeMessage(&msg, fp);
    mFHRecordGB.writeFieldMessage(0, &soc, fp);
    mFHRecordGB.writeFieldMessage(1, &voltage, fp);
} else {
    mFHRecordG.writeMessage(&msg, fp);
}
```

### Adding Developer Fields
```cpp
mFHBatteryLevelField.init({ FIT_FIELD_DESCRIPTION_FIELD_NUM_FIELD_NAME,
                            ... });
FIT_FIELD_DESCRIPTION_MESG battLevel{};
strncpy(battLevel.field_name, "batteryLevel", ...);
battLevel.fit_base_type_id = FIT_BASE_TYPE_UINT8;
mFHBatteryLevelField.writeMessage(&battLevel, fp);
```

## Advanced Topics

### FIT Timestamp Conversion
Unix timestamps are converted to FIT time by subtracting `FIT_EPOCH_OFFSET` (631065600 seconds, Dec 31, 1989).

```cpp
FIT_DATE_TIME unixToFitTimestamp(std::time_t unixTimestamp) {
    return unixTimestamp - FIT_EPOCH_OFFSET;
}
```

### Data Scaling
- Altitude: `(altitude + 500) * 5` (stored in mm, offset for negative values)
- Speed: `speed * 1000` (mm/s)
- Distance: `distance * 100` (cm)
- Time: `time * 1000` (ms)

### GPS Coordinates
Latitude/Longitude converted to semicircles: `degrees * (2147483648.0 / 180.0)`

### CRC Calculation
CRC is calculated over the entire file (header + data) using `FitCRC_Update16()`.

### File Size and Header Update
The header is written initially with dummy data size, then updated in `stop()` with the actual size.

This structure ensures FIT files are valid, compact, and compatible with standard FIT parsers like those in Garmin Connect or third-party tools.
